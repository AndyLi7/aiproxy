# B2 C：准入存储与部署证据契约（待接入）

本文件是 G1/G2/G5 的本地实现边界和部署适配契约，不是可上线结论。G3 已单独交付。新增代码当前没有请求入口、HTTP 管理入口或 status 能力声明，没有自动迁移和生产部署验证器。缺少部署验证器时拒绝 seal/新准入；已持久接纳的同一请求可读取，不能把读取旧记录解释为再次发送许可。

## 持久协议基础

- `ChannelIdentityOf` 绑定物理 ID、完整 key 摘要和身份 hash，后者包含 type/base URL/proxy/TLS 及全部非 routing-only configs；模型、sets、状态和报价不进身份。记录中不保存 key 明文。
- 五张独立表分别保存控制行、已验证证明/撤销记录、已封住的摘要家族、不可变操作屏障和使用记录。控制行通过数据库写锁串行化准入、后继授权与屏障，SQLite 不依赖进程 mutex；请求预留回调与使用记录在同一事务落库。
- 同 key 迁移只授权精确后继 ID/hash，别名及之后新建的同摘要 demo/trial/probe 不继承授权。连续迁移推进家族后继；换 key 封住整个旧家族，回退只能匹配指定已记录操作的精确逆向身份。操作 hash、epoch、revision CAS 控制重放。
- 已接纳使用记录保留原身份和服务端数据库时间。未知接受、未完成使用没有自动到期转零的逻辑。下一阶段才实现有证据的关闭、活动 owner/lease 核对、最终停用及上游吊销确认，当前不提供安全停用命令。
- 当前仅 PostgreSQL/SQLite 且 DB/LogDB 为同一个连接对象。不同对象即使指向同库也保守拒绝，不猜测跨库原子性；MySQL 拒绝新增 C 协议写入，不改变原队列或普通请求。
- SQL 仅为 `core/migrations/channel-admission-v1/` 中的审阅草案，空 epoch 不激活 C。生产应用必须另行审阅。缺表/列/错误版本拒绝，绝不创建缺失表来伪造就绪。

## 部署证据的签发责任与缺口

签发者必须是能够控制目标环境全部入口流量及副本准入的部署控制面，而非当前网关进程、应用管理员勾选、客户 header 或自报 heartbeat。目前尚未核实这个控制面的实际系统、服务账号、签名密钥和证明读取接口，**因此没有可用生产签发者，也不能激活 C**。本轮不会创建一个虚构签发服务或读取真实控制面。`LoadDeployment` 只提供服务端已验证本地事实快照的注入点，测试中的成功验证器使用明确的合成 epoch，生产没有默认成功实现。

后续适配器须提供以下可核实字段，实际签发方、密钥来源、撤销读取接口及环境标识需由主控确认后绑定：

| 字段 | 必须证明的事实 |
| --- | --- |
| issuer / key ID / audience | 被配置为可信的部署身份，目标仅为该环境的迁移服务，不能跨测试服/正式服复用 |
| environment / service IDs | 精确服务集合，包含普通与流式 relay、image/native、内部指定渠道、管理 demo/trial、异步/恢复 worker |
| ingress IDs / policy digest | 全部可到达入口使用强制 build/epoch 许可名单；旁路入口被禁用或同样围栏化 |
| build SHA / admission protocol / storage version | 每个允许承接流量的构建均执行协议 v1，使用同一已审存储，不允许旧二进制混入 |
| epoch / monotonic sequence / membership digest | 明确的一代部署和成员集合，扩缩容或构建变化必须先证明后放流量；不能复用过期拓扑 |
| issuedAt / expiresAt / proof ID | 使用服务端可信时间，拒绝未来签发、过期和重复激活；建议最多五分钟有效期，最终值需配合控制面实际续期能力验证 |
| revocation cursor / freshness | 可证明当前未撤销且撤销视图足够新；签名正确不能替代撤销和入口现状验证 |

验证器必须先校验签名、受众、精确环境/服务/入口范围、协议/存储和成员，再校验时效、撤销及单调序号。激活时还要原子保存绑定的 epoch/证明摘要和已消费 proof ID；内部 `Activate` 已校验 proofID 单次消费、单调 sequence、成员/执行者/存储绑定，重复返回不刷新有效期；仍没有生产 HTTP 激活 API 或实际签发/刷新适配器。仅验证一张签名凭证但无法证明入口持续围栏，仍拒绝。

## 最小兼容发布与回滚顺序（方案，未执行）

1. 审阅、备份并应用附加存储，保持空 epoch。先发布能识别持久屏障的版本到全部服务及恢复 worker；这一阶段不开启迁移。
2. 控制面先建立入口许可名单和副本准入约束，确认全部流量只进入具备相同协议的构建，封住旧入口和旧副本；在该约束持续生效时签发目标 epoch 的证据。
3. 服务端核实证据并持久激活 epoch。先开始使用记录，再对既有任务/异步使用做保守保留核对；任何未覆盖入口、历史使用或账单依赖继续阻止 seal/commit/最终停用。实际从记录启用到可迁移的边界仍需端到端演练，不能仅靠等待三十分钟。
4. 扩容时，新副本通过协议/存储/build/epoch 准入后才进负载均衡；旧构建永远不能先接流量再补 heartbeat。成员变更由控制面重新签发并保持入口约束不中断。
5. 证据过期、撤销读取失败或入口状态不明时拒绝新的危险迁移写入；已有屏障继续强制执行，历史读取与已冻结任务恢复保留。当前基础协议对缺失证明的新准入也拒绝，未来入口接线必须验证这个降级行为，不得静默走旧无保护路径。
6. 回滚仅允许回到同样理解现有屏障和 epoch 的兼容构建，保留所有表、屏障、历史和旧 key。若要回到不理解屏障的旧二进制，必须先停止其接收受保护入口流量并完成专门审阅；不能通过关应用开关或删表来回滚。

## G5-D1：围栏覆盖执行者和已有连接

入口许可名单必须包括执行者身份（service / instance / build SHA / epoch），不能只从负载均衡摘除旧实例。证明成员集合的规范化摘要必须与控制行一致，当前进程的服务端身份必须是精确成员；合成旧 build、暂停 dispatcher、旧连接 epoch、未知新成员均被本地协议拒绝。客户 header 不参与构造执行者身份。这些测试是局部协议验证，不代表旧二进制会自行调用新协议。

实际控制面必须在激活前证明：所有新进程启动、worker 认领、恢复调度和供应商发送入口都受持续的构建/epoch 约束。已有 HTTP/流式连接不能以“连接建立时已授权”为由跳过每次新工作的持久准入；旧进程已接收但未落库的工作不能被假定不存在。暂停后恢复的 dispatcher、cron、异步账单和恢复 worker 同样需要执行者围栏，不能只枚举 HTTP 服务。

如何强制拒绝旧执行者必须由实际控制面给出可验证机制，例如其已有的工作负载身份/出口约束，或经证据确认旧执行者完全退出且不能被重启放行。目前没有核实这样的机制，因此真实激活仍拒绝。不能声称新增 Go 表查询可以约束不读取这些表的旧二进制。升级时已有冻结任务交给兼容恢复者继续原 ID/key/报价与资金流程；不得为升级直接终止客户任务。旧版本已发送但未记账的窗口作为未知使用保留，不能仅清理进程就判定客户工作结束。不兼容回滚必须被控制面的启动/流量/执行者准入规则禁止，单纯操作说明或环境变量不构成证明。

## G5-D2/D3：本地证明、最终时间 CAS 与降级矩阵

外部签名、入口/执行者现状和撤销视图由未来受信刷新适配器独立获取与验证；`LoadDeployment` 仅返回有界本地快照，不是每次请求触发网络刷新的钩子。加载发生在数据库事务外；全局 control 锁内禁止外部控制面和供应商请求，任务预留回调也仅允许有界数据库写。没有该适配器时不会使用测试成功验证器作为默认值，五分钟仍是待核实的建议，不是运行常量。

事务顺序为 control 写锁 → 需要的渠道行锁 → 本地 proof 行锁 → 新数据库时间校验 → journal/use 写入 → 最终 control CAS。最终 CAS 重新约束 epoch、sequence、存储世代、成员/执行者摘要、proofID/事实摘要、未撤销、有效期和撤销视图新鲜度。proof 撤销记录独立于全局 control 行，允许在 sealer 等渠道锁时被更新；取得 proof 锁后再读取，之后保持锁直至事务结束。暂停到 journal 写入时过期会使最终 CAS 失败并回滚。

`RecordedAtMs` 只是所有相关锁取得后的本次 journal 记录时间，**不是排空开始时间**。三十分钟起点需在屏障提交、实际选路/入口切换和回读均成功后另行持久确认；该确认和最终停用尚未实现。不能将事务开始、初次取证或 journal 记录时间直接拿来计时。

| 状态 | 新请求/新迁移 | 已持久接纳任务与幂等结果 |
| --- | --- | --- |
| 从未激活 C，且没有屏障历史 | 原请求/队列路径兼容；内部 C 操作因空 epoch 拒绝 | 原恢复路径不变 |
| 已激活，当前本地证明有效，执行者/存储匹配 | 新准入执行持久协议，旧家族只放精确后继；迁移仍需其他 C2 条件 | 读取原事实，按冻结身份恢复 |
| 已激活，证明过期、撤销或撤销视图未知 | 当前保守范围为所有经过受保护网关入口的新准入及 seal/激活变化拒绝；不能走旧无保护路径 | 已记录同一请求和操作结果不等待外部取证、不刷新权限；继续合法恢复，不能重发一次新请求 |
| 已有屏障后关闭应用迁移开关 | 停止新迁移；已有屏障及受保护入口协议继续强制执行 | 历史/恢复继续，不能删除屏障或凭据 |
| 存储缺失/版本未知/世代或水位不可信 | 新 C 操作拒绝，不能将缺表当零 | 保留旧身份和未知使用；具体恢复路径必须在接线中验证，不伪造排空 |

这是待接入运行时入口的状态矩阵；当前代码未接线，因此不能声称普通/流式/native/image/admin 的真实行为已覆盖。

## G5-D4：数据库恢复水位与一次激活

已验证事实绑定独立于被恢复数据库的 `StorageGeneration` 和 `StorageWatermark`。当前控制行世代不匹配、或本地 journal revision 低于受信最低水位时，激活和新工作拒绝；不能用新 proof 把旧快照包装成最新状态。隔离测试以真实 SQLite `VACUUM INTO` 保存封口前快照，再建立屏障，随后使用独立较高水位访问旧快照，确认无新准入/屏障写入。重开读取旧记录仍保留原身份。

proofID 通过 proof 表主键和 `consumed_sequence` 只在激活/成员变更时消费一次。当前激活的同一事实重复调用只返回原记录，不刷新时效；普通 Admit/Seal 重查不重复消费。已有更新 sequence/成员后，旧 proofID 不能再激活；换存储世代不能自动放行，须走另行审阅的恢复流程。

真正的备份恢复程序必须在切换数据库前由控制面撤销旧缓存/epoch、维持执行者围栏，并从独立账本确认最低恢复水位。屏障提交和独立水位记录的确认/未知结果处理、储存引擎回滚能否绕开该流程，尚未有真实适配器证明；若允许不受控在线回滚或仍提供旧证明快照，本地代码无法独自检测丢失的后续屏障，**因此这种环境不可激活 C**。不能因表仍存在就认为安全，也不会创建新的控制面来掩盖这一缺口。
